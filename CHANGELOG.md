# Changelog

All notable changes to Blindspot are written here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

How a release is made, and what to update with it, is in [Contributing](docs/how-to/contributing.md#releases).

## [Unreleased]

### Changed

- The image now runs Python 3.14.10, nginx 1.31.10 and PostgreSQL 18.7, the latest patch releases. The build fails if a lower version would be installed, the smoke test checks the running container, and CI uses the same Python and PostgreSQL.
- Fix the Agents page's SonarQube findings and add browser coverage for following a mission.

### Added

- Tool manifests and the tool registry: a validated description of each tool (risk class, capabilities, typed parameters, timeouts, output cap, plain-language explanation), a command-line builder that fills one argument for each value and never makes a shell string, bundled manifests as YAML, and administrators' custom tools (ids start with `x.`) with a read, preview and edit API.
- The tool scope guard and the permission policy: every target of a tool call is looked up and checked address by address against the pentest's scope (loopback, metadata and other never-reachable addresses are always refused, ranges and whole-host scans need the whole host or range in scope), and a rule table decides per agent role, tool and pentest whether a call runs on its own, asks a person or is denied. Intrusive tools always ask, destructive tools are off, and a kill switch and a paused pentest stop everything. Administrators manage the rules and the kill switch through the API, and every decision has a plain-words reason.
- The core tool pack: manifests for Nmap, sqlmap, Nuclei, ffuf, testssl.sh, wafw00f, httpx, WhatWeb and Nikto, and five built-in tools (headers, cookies, CORS and CSP; a JWT inspector; robots, sitemap and security.txt; a form and parameter spider; a session token strength check). One result shape for every tool, with hardened parsers for each tool's output (no XML entity is expanded, nesting, size and list length are capped), tested on real captured output, and a plain-words summary of any result. The image now includes nmap, sqlmap, `dig` and `whois`; the bigger tools are installed by the runner.
- Results: every pentest keeps the results of tool runs, imported tool output and notes written by hand. Each result can be read in plain words (with a port map, a TLS grade and a header scorecard), as sortable tables, or as the raw output with the command, search, copy and download, and the view each person picks is remembered. Credentials a tool finds are sealed and masked, and showing one is audited. Results can be searched and filtered, tagged, deleted to the trash and restored, singly or in bulk. Promoting a result to a finding and explaining one with an agent come with later tickets.
- The agent runtime: a mission plans the pentest's tests in code (observing categories first, then active, then intrusive; tests that need what the target does not show, that a person already settled, that are above the pentest's risk limit or that are for a person are skipped with the reason) and runs them with category agents and model-driven test agents. Every tool request goes through the manifest checks, the scope guard and the permission policy whatever the model says, a step runs once and is never repeated after a restart, step, token, cost and time caps and the kill switch are read from the database before every step, a step that needs approval waits for an administrator and is checked again when approved, and a finding is replayed by a verifier before it counts. A model can raise a test's verdict but never lower one. Missions are started, paused, resumed, cancelled and followed through the missions API with an event log. The tool runner that executes steps is a separate ticket, so missions answer `no_runner` until one is connected.
- The Agents page and agent settings: the commander, a category agent per category and a test agent per test with their runs, success rate, cost and last run (tree or grid, search, filter by risk); the default caps of a mission and three presets (passive recon only, safe full assessment, deep dive); immutable prompt versions for the test agent and the verifier with a line diff, choosing a version and putting the built-in one back, recorded on each mission; and a deploy flow on a pentest that previews what a mission would run and spend, asks for a confirmation of the scope (which the server requires) and then follows the mission with approvals, pause, resume and cancel. Changes to caps and prompts are audited. Settings that differ per category or test and custom agents come later.
- `make up` builds the image and starts Blindspot, `make down` stops it and keeps all data, and `make delete` removes everything including the volumes and the build cache after asking for confirmation. CI tests that the data survives `make down` and `make up`.

## [0.0.1] - 2026-11-25

The first version: the foundation of the platform. It has the container, sign-in and the secrets vault, the AI provider settings, the methodology engine with the OWASP WSTG checklist, and pentests with their authorization gate, scope and checklist. The agents and the security tools come in the next versions, so this version cannot run a test yet.

### Added

- **Single container** with nginx and TLS (a self-signed certificate on the first start), the API and PostgreSQL 18 on a unix socket with no password, supervised by s6. The image is built from a digest-pinned Wolfi base, runs read-only with its capabilities dropped, and shuts down cleanly. The database is migrated when the container starts, after a `pg_dump` copy when the structure will change.
- **Continuous integration**: formatting, actionlint, ShellCheck and hadolint (from images pinned by digest), ruff, pyright, bandit, ESLint and vue-tsc, pytest and Vitest with coverage, Playwright against the API and against the real image (three shards each, with merged browser coverage), Trivy for dependencies, secrets and the image, CodeQL, zizmor, SonarQube with a quality gate and a report of what it found, and a ticket-key check on every branch, commit and pull request title. Dependabot raises weekly updates.
- **Release workflow** that builds, scans and smoke tests the image for amd64 and arm64, publishes a multi-platform image to the GitHub Container Registry with signed build provenance and SBOMs, and attaches the SBOMs to the release.
- **Backend** on FastAPI with SQLAlchemy 2 (async), psycopg 3 and Alembic, with structured logs that redact secrets, one error shape for every failure, and a health route that reports the release.
- **Secrets vault**: AES-256-GCM sealing with a key per purpose derived by HKDF-SHA256, sealed column types, an app secret key that can be rotated, and log redaction.
- **Accounts**: first-run setup with a setup code, Argon2id passwords (the hash is sealed too), sessions, administrator and viewer roles, sign-in lockout, CSRF checks, passkey (WebAuthn) sign-in with user verification and clone detection, and an audit log.
- **Web app** on Vue 3, Vuetify and TypeScript: the Situation Room design in a dark and a light theme, a collapsible menu built from the router, a command palette, a switch for visual effects, shared loading, empty and error states, and a layout that works on a phone. Dialogs have accessible names, and axe checks every page in both themes.
- **Pages** for first-run setup, sign-in, passkeys and the account, for users and the audit log (administrators), and for the terms of use.
- **Terms of use** that everyone accepts before using the app, versioned by a fingerprint of the words, with `DISCLAIMER.md`, `ACCEPTABLE_USE.md` and `SECURITY.md`.
- **AI providers**: Anthropic, OpenAI and Ollama (local and cloud) behind one interface on Pydantic AI, keys sealed in the vault, an address guard that refuses private and metadata addresses for hosted providers, test connection, fetch models, a price catalog with overrides, a usage ledger with token classes and cost, monthly budgets with a hard stop, a default model for each agent role, and a settings page for all of it.
- **Methodology engine**: methodologies as data (YAML packs), the OWASP WSTG checklist (13 categories, 133 tests) imported and mapped to tools, playbooks for each test, and a Methodologies page.
- **Pentests**: create, edit, clone, archive, trash, restore, export and import; a scope compiler that refuses ranges and addresses it must never allow; an authorization gate and status lifecycle (permission statement kept with who agreed, when and from where); a per-pentest checklist with status, notes, evidence links and custom tests; authorization warnings in the forms and a launch dialog that lists what will run.
- **Documentation**: the platform plan, research notes, a guide for each part, the logo, and the Apache License 2.0.
